# Accepted task handoffs

`features.task_handoffs` is disabled by default and also requires selected deliverable bundles. Administrators can enable both in Settings or the installer. Current named workspace membership, operate permission and suite scope constrain the sender and recipient. The task Copilot family uses the same native services and receipts.

The sender first shares an exact selected bundle, then opens **Offer a separate task handoff**. The review identifies the recipient, selected versions and file hashes, next-work instructions, sender-declared commitments, source task recorded cost, unanswered question count, new task dollar ceiling, expiration, and the conversation/subtasks that acceptance closes. Outside commitments are not inferred from incomplete local records.

An offer grants no execution authority. The named recipient must explicitly accept. Acceptance acquires the same non-reentrant execution leases as the common runner, including all source conversation descendants; it refuses active or unsettled work. Leases remain held until execution finalization has ended. SQLite uses local interprocess leases; PostgreSQL uses a dedicated bounded session advisory lock across replicas, without holding a world transaction through model calls. There is no timeout-based takeover of a live lease.

One world transaction creates a **blocked, unstarted recipient-owned successor**, copies only the selected artifact/evidence bytes, saves original-author/source-version lineage, and closes the source conversation tree to further execution. Original task ownership and its private conversation are preserved. The former owner receives lineage metadata, not access to the recipient's task. Current task authority surfaces the closure; common execution, chat follow-up and restart gates enforce it. The recipient reviews the new task and explicitly resumes when ready. Connections, credentials, learned memory, project memberships and knowledge-source bindings are never copied. The recipient must select their own currently authorized sources and connections.

The accepted ceiling persists on the successor. Common execution clamps available dollars against the recorded ceiling and previous task/descendant episode spend; inherited child execution shares this remaining ceiling. Historical parent summaries can include child spend, so this accounting can conservatively stop early; it never grants additional dollars. existing administrative and organization limits can only tighten it. Acceptance itself does not invoke models, start a runner, or send a message externally.

Native acceptance and lineage receipts survive a governed-offer publication interruption. Read and exact retry recover the already-created successor; a distinct response cannot create another one. Source closure is durable even when the feature is later disabled. Withdrawal or expiry stops future unaccepted offer access; source bundle revocation also stops acceptance. Once accepted, the selected copies belong to the recipient's task. Neither withdrawal nor revocation claims to erase downloaded or accepted copies, or to undo external effects from earlier work.

Limits: leases on a shared PostgreSQL or distributed deployment and the installed browser journey are not qualified.
